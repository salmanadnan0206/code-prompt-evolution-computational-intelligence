\begin{conceptbox}{Why two Gemini models?}
\textbf{Gemini 2.5 Flash} generates C++ code (cheap, deterministic at temperature~0) ---
this is the model being \emph{optimised}.
\textbf{Gemini 2.5 Pro} performs crossover and mutation (creative, temperature~0.7) ---
this is the evolutionary \emph{operator}.
Both models are called via the \texttt{google-genai} Python SDK with service account
authentication --- no interactive login or API key is required.
Despite Pro costing $8\times$ more per output token, it accounts for under 30\% of
the total bill because it is used rarely (66 calls vs.\ 4,425 Flash calls).
\end{conceptbox}

\begin{warnbox}{Thinking tokens are billed at the output rate}
Gemini 2.5 models produce internal chain-of-thought (\emph{thinking tokens}) before
the visible response.  These tokens are \textbf{not shown} in the response text but are
reported in \texttt{usage\_metadata.thoughts\_token\_count} and billed at the standard
output token rate.  The project tracks and records them in \texttt{calls.jsonl}.
Budget: 512 thinking tokens for Flash (fitness), 2048 for Pro (operators).
Actual usage is typically 200--400 thinking tokens for Flash and 800--1500 for Pro.
The output token figures in this document \textbf{include thinking tokens}.
\end{warnbox}

\subsection*{Key assumptions}

\begin{itemize}[nosep]
  \item Population size = 5, ELITISM\_COUNT = 0 $\Rightarrow$ all 5 slots are bred fresh each generation.
  \item Total offspring across 12 generations = $5 \times 12 = 60$.
  \item All 60 offspring are eligible for crossover (rate = 0.80) $\Rightarrow$ $60 \times 0.80 = 48$ crossover calls.
  \item Only offspring beyond CROSSOVER\_ONLY\_SLOTS=2 are mutation-eligible:
        $3\ \text{slots/gen} \times 12\ \text{gen} = 36$ mutation-eligible offspring.
  \item Mutation probabilities are independent: inject~0.25, delete~0.15, rephrase~0.10.
        Expected calls: $36 \times 0.25 + 36 \times 0.15 + 36 \times 0.10 = 9 + 5.4 + 3.6 = 18$ mutation calls.
  \item Holdout evaluation runs in parallel using ThreadPoolExecutor (200 calls, all Flash).
  \item Early convergence can reduce generations below 12; counts above assume no early stop.
\end{itemize}

\begin{conceptbox}{CROSSOVER\_ONLY\_SLOTS reduces operator calls}
CROSSOVER\_ONLY\_SLOTS=2 means 2 of 5 offspring per generation skip all mutations.
Across 12 generations this saves $24 \times (0.25 + 0.15 + 0.10) = 12$ expected Pro
calls --- a small but non-negligible saving given Pro's high output token cost.
\end{conceptbox}

\section{What Are Thinking Tokens?}

Gemini 2.5 Flash and Pro produce internal chain-of-thought reasoning (\emph{thinking})
before generating the visible response.  Thinking tokens:
\begin{itemize}[nosep]
  \item Are \textbf{not} visible in the response text.
  \item Are reported in \fn{usage\_metadata.thoughts\_token\_count}.
  \item Are \textbf{billed at the same rate as output tokens}.
  \item Are tracked by \texttt{cost\_tracker.py} and included in \texttt{calls.jsonl}.
\end{itemize}

The project configures thinking budgets via \fn{ThinkingConfig(thinking\_budget=N)}:
\begin{itemize}[nosep]
  \item \textbf{Flash (fitness)}: \fn{thinking\_budget=512}. Typical actual usage: 200--400 tokens.
  \item \textbf{Pro (operators)}: \fn{thinking\_budget=2048}. Typical actual usage: 800--1500 tokens.
\end{itemize}

\chapter{Optimisation Options}
% ======================================================================

\section{Cost Reduction Levers}

\begin{enumerate}
  \item \textbf{Reduce evolution pool size} (65 $\rightarrow$ 30--50 problems): Proportionally
        reduces Flash fitness calls.  50 problems would save $\sim$23\% on Flash costs.

  \item \textbf{Reduce generations or population}: With POPULATION\_SIZE=5 and GENERATIONS=12,
        there is limited room here without hurting GA quality.  The convergence detection
        (CV threshold) already terminates early when the population converges.

  \item \textbf{Disable or reduce thinking budget}: Setting \fn{thinking\_budget=0} halves
        the estimated cost to $\sim$\$1.40.  This trades reasoning quality for cost.

  \item \textbf{Use Gemini 2.0 Flash} (\$0.10/\$0.40 per MTok) for fitness calls:
        Would reduce Flash cost by 33\%.  Gemini 2.0 Flash does not support thinking tokens,
        so output cost per call drops to $400 \times \$0.40/\text{MTok} = \$0.00016$.
        Flash fitness cost: $4{,}425 \times \$0.00016 = \$0.71$ (vs.\ \$2.13 with 2.5 Flash).

  \item \textbf{Early convergence stop}: The GA already implements CV-based early stopping.
        If the population converges at generation 8, cost is roughly 67\% of the full run.
\end{enumerate}

\chapter{Runtime Cost Tracking}
% ======================================================================

The \texttt{cost\_tracker.py} module logs every API call's exact token count and
computes the real cost in real time.  Three separate files are updated during the run:

\begin{enumerate}[nosep]
  \item \textbf{\texttt{run\_*/calls.jsonl}} --- streaming JSONL, one line per API call,
        written immediately after each call (no buffering).
  \item \textbf{\texttt{run\_*/costs\_live.json}} --- live running-total summary, overwritten
        after every call; shows up-to-date spend during a long run.
  \item \textbf{\texttt{Costs/cost\_\textless run\_name\textgreater.json}} --- same live summary written to the
        \texttt{Costs/} directory, named after the run directory (e.g.\
        \texttt{cost\_run\_20240501\_143022\_tournament.json}).
        Updated after every API call so you can monitor spend during a long run
        without opening the run directory.
\end{enumerate}

At run end, \texttt{tracker.flush()} writes the final summary:

\begin{verbatim}
Costs/cost_<TIMESTAMP>.json:
{
  "grand_total_estimated_usd": 2.99,
  "total_llm_calls": 4491,
  "total_input_tokens": 1784520,
  "total_output_tokens": 3181980,
  "breakdown_by_phase": {
    "fitness":        { "calls": 4425, "input_tokens": 1770000,
                        "output_tokens": 3097500, "total_cost_usd": 2.125 },
    "crossover":      { "calls": 48,   "input_tokens": 10560,
                        "output_tokens": 61440, "total_cost_usd": 0.628 },
    "mutate_inject":  { "calls": 9,    "input_tokens": 1980,
                        "output_tokens": 11520, "total_cost_usd": 0.118 },
    "mutate_delete":  { "calls": 5,    "input_tokens": 1100,
                        "output_tokens": 6400,  "total_cost_usd": 0.065 },
    "mutate_rephrase":{ "calls": 4,    "input_tokens": 880,
                        "output_tokens": 5120,  "total_cost_usd": 0.052 }
  },

    "gemini-2.5-flash": { "calls": 4425, "total_cost_usd": 2.125 },
    "gemini-2.5-pro":   { "calls": 66,   "total_cost_usd": 0.863 }
  }
}
\end{verbatim}

Each run creates a \textbf{new file} (timestamped) --- prior runs are never overwritten.
This gives a complete cost history across all experiments.

\begin{conceptbox}{Resume and cost continuity}
When \texttt{main.py} is invoked with \texttt{--resume}, it calls
\texttt{tracker.restore\_from\_jsonl(run\_dir / "calls.jsonl")} to replay all existing
call records and restore running totals.  The final cost summary therefore reflects
the entire run --- both the pre-crash portion and the resumed portion --- with no
double-counting.
\end{conceptbox}

Individual JSONL entries in \texttt{calls.jsonl} look like:
\begin{verbatim}
{"t": "14:32:07", "phase": "fitness", "model": "gemini-2.5-flash",
 "in": 412, "out": 693, "cost": 0.000477, "total_calls": 47,
 "running_cost": 0.022419}
{"t": "14:33:51", "phase": "crossover", "model": "gemini-2.5-pro",
 "in": 228, "out": 1340, "cost": 0.013685, "total_calls": 48,
 "running_cost": 0.036104}
\end{verbatim}

The \texttt{out} field includes both visible response tokens and thinking tokens.
The \texttt{cost} field is computed from the \texttt{PRICING} table in
\texttt{cost\_tracker.py} using the exact token counts reported by the SDK.
